## Cross-cutting themes

1. **Silent failure is the house style.** Blanket `catch { }` / `catch → return false` with a discarded result appears in the tag writer, the persistence loader, the trash helper, the metadata finder, `StartupHelper`, and both scrobblers. Several of the worst findings below are not "the code does the wrong thing" but "the code fails and tells nobody, then overwrites the good state with the bad".
2. **No backups anywhere.** `library.json`, `settings.json`, `playlists.json` and the user's audio files are all overwritten in place or via a non-fsynced rename, with no `.bak` and no corrupt-file quarantine. Three separate CRITICALs collapse into "one bad read silently becomes a permanent write".
3. **Heavy work on the UI thread.** Image decode + per-pixel analysis at every track change, TagLib opens inside settings-slider handlers, full-library passes on tab open, per-keystroke library scans, filesystem stats in list templates. The app has good `Task.Run` patterns in places — they just aren't applied consistently.
4. **Windows is the tested platform.** CI runs tests on `windows-x64` only; macOS/Linux get no test execution, no credential encryption, no media-key integration, and the queue popup doesn't open at all.
5. **Dead or unreachable features.** The LRC sync editor, "Save Queue as Playlist", shuffle in the main window, the m3u URI decoder, `IUnifiedLibraryService`, `IOfflineCacheService`, `RefreshPlaylistCountAsync`, and 11 persisted settings have no UI or no caller.

# 1. Audio Playback Core & Output Pipeline

### HIGH

#### Volume slider goes dead after any audio-setting change while Song Transitions is on
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:599`
- **What's wrong:** `Volume` (599), `VolumeAdjust` (614), `CommitVolume` (647) and `ReapplyVolume` (1499) all early-return when `_crossfadeEnabled && _currentMedia != null`. `_crossfadeEnabled` is only cleared inside a transition (1923 / 2102 / 2275 / 2421), but `SettingsViewModel.ApplyAudioSettings()` arms it unconditionally at `src/Noctis/ViewModels/SettingsViewModel.cs:1018` and is invoked from ~9 settings handlers (1475, 1482, 1491, 1498, 1505, 1519, 1525, 870, 2838). Repro: play a track, then flip Settings → Song Transitions on (`TransitionStyle` defaults to `"Crossfade"`, `AppSettings.cs:100`). `_crossfadeEnabled` is now true with a loaded media, so every subsequent volume write is swallowed — the slider moves, the audio level does not — until the next `PlayInternal` runs.
- **Fix:** Stop using `_crossfadeEnabled` as both "feature is configured" and "a transition is in flight". Add a separate `_transitionInFlight` flag set only by the fade paths and checked by the volume guards, or drop the guard entirely and let the fade workers park the ramp (they already do, 2005/2170/2340).

#### Exclusive mode applies the user's volume twice and is not bit-perfect below 100%
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:1896`
- **What's wrong:** In `PlayInternal` the branch order is `fadeInMs > 0` → `_sessionVolume != null` (1896) → `ActiveCallbackSink == null` (1911). On Windows `_sessionVolume` is non-null by default (505), so with Exclusive Mode on, line 1909 writes `_player.Volume = MilliToPlayerVolume(milli)` instead of the pinned 100 that `RebuildOutputModeLocked` set at 1319. With amem no `volume_set` callback is registered, so LibVLC applies that volume as a software multiply on the PCM *before* it reaches `AudioPlay`; `GainSampleProvider` (`WasapiGainOutput.cs:336`) then applies `WasapiGainLevel()` again. At slider 30 that is ≈ −5 dB too quiet, and at any level < 100 the "bit-perfect" claim in `OutputDescription` (1206) is false. The same ordering bug is in the seek worker (`3189` before `3214`), and `ScheduleSessionVolumeReassert` (2723) is gated only on `_sessionVolume == null` (2725) — not on `ActiveCallbackSink` — so when the exclusive open falls back to the shared NAudio sink (1409) it also drives that sink's process session, a third attenuation.
- **Fix:** Check `ActiveCallbackSink != null` before the `_sessionVolume` branch in all three places; on the callback path pin `_player.Volume = 100` and let the sink own gain, matching `ScheduleVolumeWrite` (735) and `CommitVolume` (652).

#### `Resume()` blocks the UI thread on `_playbackLock` with no timeout
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:2767`
- **What's wrong:** Every other public playback entry point queues to the ThreadPool (`Play` 1710, `Stop` 2801, `PrepareNext` 1596, `SetExclusiveMode` 1237), but `Resume()` calls `_playbackLock.Wait()` inline. `PlayerViewModel.PlayPause()` (`ViewModels/PlayerViewModel.cs:224`) is a `[RelayCommand]`, so this runs on the UI thread. Lock holders include `PrepareNext`'s **non-cancellable** `parseTask.Wait(8000)` (1625) and the native `_player.Stop()` in `Stop()` (2809)/`PlayInternal` (1848). Repro: AutoMix/gapless prepares the next track from a slow or network path, user pauses then presses play — the window is frozen for up to 8 s.
- **Fix:** Queue `Resume` to the ThreadPool like the other operations, or use `_playbackLock.Wait(TimeSpan)` with a short bound and fall back to an unlocked `_player.Pause()` toggle.

#### Unconditional disk logging on the WASAPI render thread, into a file on the user's Desktop
- **File:** `src/Noctis/Services/WasapiGainOutput.cs:296`
- **What's wrong:** `Diag` is not gated by any env var or setting and does `File.AppendAllText` under a process-wide lock. It is called from `GainSampleProvider.Read` (360-361, the WASAPI render callback — every 400 reads), from `Write` (235-236, LibVLC's audio thread, every 200 buffers) and from `VlcAudioPlayer.AudioPlay` (`VlcAudioPlayer.cs:2650`). Any disk stall (AV scan, OneDrive-redirected Desktop, spinning disk) blocks the render thread inside its buffer-fill deadline → underrun, which is precisely what exclusive mode exists to avoid. It also drops an unexplained, unbounded `noctis_wasapi.log` on the Desktop of anyone who enables Exclusive Mode (a shipped setting, `Views/SettingsView.axaml:1738`).
- **Fix:** Gate `Diag` behind an env var / Developer Mode like `NOCTIS_VLC_LOG`, and never call it from `Read`/`Write`/`AudioPlay` — push to a lock-free ring buffer drained by a background thread if the data is still wanted.

#### Exclusive-mode sink has no device-loss recovery; a dead sink stalls LibVLC's audio thread 2 s per buffer
- **File:** `src/Noctis/Services/WasapiGainOutput.cs:219`
- **What's wrong:** `Write` spins `Thread.Sleep(2)` for up to 2000 ms waiting for room, then `AddSamples` throws "buffer full" (caught at 238, which then does a disk write). Nothing subscribes to `WasapiOut.PlaybackStopped`, and nothing follows the default-device change (unlike `WasapiSilenceKeepAlive.DefaultDeviceChanged`, `WasapiSilenceKeepAlive.cs:265`). If the USB DAC/BT endpoint is unplugged or the default device is switched mid-track, NAudio's render thread stops, `_buffer` fills permanently, and every LibVLC audio callback then costs 2 s + a file append. Result: permanent silence with the transport still running, and `_player.Stop()` (which joins the aout thread) blocked behind the stalled callback while holding `_playbackLock`.
- **Fix:** Subscribe to `WasapiOut.PlaybackStopped`, mark the sink faulted, and have `Write` drop instead of spinning; add a default-device change check (reuse the keep-alive's polling) that disposes and re-opens `_exclusiveOut` and raises `OutputModeChanged`.

### MEDIUM

#### `ApplyReplayGain` parses the audio file's tags synchronously on the UI thread
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:1472`
- **What's wrong:** `ApplyReplayGain` → `ReadReplayGainTags` → `TagLib.File.Create(filePath)` (1518) is a blocking open+parse of the currently playing file. It is called on the UI thread from `SettingsViewModel.ApplyAudioSettings` (`SettingsViewModel.cs:1022`, reached from ~9 settings handlers) and, worse, from `OnReplayGainPreampDbChanged` (`SettingsViewModel.cs:1700`) — once per tick while dragging the pre-amp slider (see §2). On a NAS/removable-drive library this stalls the UI for the duration of the file open.
- **Fix:** Cache the parsed `(track, album)` gains per `_currentMediaPath` (they only change when the track changes, and `PlayInternal` already re-reads at 1762 on the worker), and make the public `ApplyReplayGain` recompute from the cache without touching disk.

#### amem delegates can be unrooted while LibVLC still holds the function pointers
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:491`
- **What's wrong:** LibVLCSharp does not keep a reference to the delegates passed to `SetAudioCallbacks` — the class comment at 111-113 says so explicitly. In the ctor, `SetAudioCallbacks` runs first (481); if `SetAudioFormat` (482) or `_player.Volume = 100` (483) then throws, the catch nulls `_audioPlayCb`/`_audioPauseCb`/… (491-492) while libvlc still holds the registered native thunks for this `MediaPlayer`. The delegates become collectable and the next amem callback calls freed memory. (`RebuildOutputModeLocked` gets this right with `??=` at 1304-1308.)
- **Fix:** Never null the delegate fields once `SetAudioCallbacks` has been called on a player; keep them alive for the player's lifetime and only drop the sink.

#### Total output failure in exclusive mode is silent — no notice, no fallback
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:1413`
- **What's wrong:** When both `TryCreateExclusive` and `TryCreate` return null, `PrepareExclusiveOutputFor` logs a `DebugLogger.Warn` and returns (1417-1419) without calling `SetAudioFormat`, without raising `OutputModeChanged`, and without disabling the amem callbacks. `AudioPlay` then finds `ActiveCallbackSink == null` (2647) and drops every buffer: the clock runs, the position bar and lyrics advance, and there is no sound and no message. The comment claims "VLC reports the aout failure", but amem succeeded, so VLC reports nothing.
- **Fix:** On total sink failure, raise `OutputModeChanged` with a user-visible reason and turn exclusive mode off (`_exclusiveModeEnabled = false` + `RebuildOutputModeLocked(false)`) so playback falls back to LibVLC's own mmdevice output.

#### `AudioPlay` sizes the native copy from the sink's channel count, not the format pinned on the player
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:2648`
- **What's wrong:** `bytes = count * sink.Channels * 2` assumes the sink's channel count equals what `SetAudioFormat` pinned. `PrepareExclusiveOutputFor` assigns the new sink (1422) *before* `_player.SetAudioFormat(...)` (1433), and that call sits inside the method-wide `try` whose catch only logs (1441-1444). If it fails after a 1-channel → 2-channel sink swap, VLC keeps delivering mono blocks while `Marshal.Copy` (2654) reads twice the block length — the exact over-read class that produced the 0x80131506 exclusive-mode crash noted in the comment at 2639-2642. The `checked(...)` cast and `ArrayPool.Rent` at 2648/2651 are also outside the `try`, so anything they throw escapes into libvlc's aout thread and kills the process.
- **Fix:** Store the channel count actually accepted by `SetAudioFormat` in a field and use that in `AudioPlay`; treat a `SetAudioFormat` failure as a sink failure (dispose the sink so `AudioPlay` no-ops). Move the size computation and `Rent` inside the `try`.

#### `_positionTimer.Start()` in `OnEndReached` runs outside the handler's try/catch and after `Dispose` freed the timer
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:2961`
- **What's wrong:** `Dispose()` disposes `_positionTimer` at 3300 but only unsubscribes `EndReached` at 3307-3310. An `EndReached` landing in that window reaches line 2961, which is outside the handler's only `try` (2948-2956), and `System.Timers.Timer.Start()` on a disposed timer throws `ObjectDisposedException`. The handler is invoked from LibVLC's native event thread, so the exception unwinds into native code and terminates the process instead of being caught.
- **Fix:** Unsubscribe `EndReached`/`EncounteredError` before disposing the timer, and wrap the whole `OnEndReached`/`OnError` bodies in `try { … } catch { }` — nothing raised from a native callback may escape.

#### Keep-alive is left suspended when the exclusive open falls back to shared
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:1322`
- **What's wrong:** `RebuildOutputModeLocked(true)` parks the silent keep-warm stream because "the endpoint is held exclusively". When `TryCreateExclusive` later fails and `PrepareExclusiveOutputFor` falls back to a shared sink (1409), nothing calls `_keepAlive.SetSuspended(false)`, so the cold-device protection stays off for the rest of the session even though the endpoint is shared again.
- **Fix:** Call `_keepAlive?.SetSuspended(sink.IsExclusive)` after the sink is created in `PrepareExclusiveOutputFor`.

#### No output-device selection anywhere in the audio path
- **File:** `src/Noctis/Services/WasapiGainOutput.cs:114`
- **What's wrong:** Every output path hard-targets the OS default endpoint: `GetDefaultAudioEndpoint(DataFlow.Render, Role.Multimedia)` for both sinks, `--aout=mmdevice` with no `--mmdevice-audio-device` (`VlcAudioPlayer.cs:405`), and the keep-alive (`WasapiSilenceKeepAlive.cs:126`). A grep of `src/Noctis` for `OutputDevice`/`SetOutputDevice` returns zero hits. A music player with a bit-perfect Exclusive Mode is exactly where users expect to pick a specific DAC rather than reroute the whole system.
- **Fix:** Enumerate render endpoints, persist the chosen device id, and pass it to `WasapiOut(MMDevice, …)` and to LibVLC via `MediaPlayer.SetOutputDevice`. Surface it on the Audio tab (`Views/SettingsView.axaml:1726`).

### LOW

#### `Stop()` clears the pending seek without taking `_seekGate`
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:2797`
- **What's wrong:** `_latestSeekMs` is otherwise written under `lock (_seekGate)` (2900-2903, 3135-3139). `Stop()` (and `PlayInternal` 1754, `RebuildOutputModeLocked` 1273) use `Interlocked.Exchange` instead, so a `Seek()` racing a `Stop()` can write its target after the clear and have the seek worker apply it to the next track.
- **Fix:** Use `lock (_seekGate) { _latestSeekMs = -1; }` everywhere, matching `Seek()`.

#### A fresh OS thread is created for every seek burst
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:3123`
- **What's wrong:** `EnsureSeekWorker` builds and starts a new `Thread` (started at 3261) each time the gate transitions 0→1 — once per scrub gesture, plus once per lyric-line click. Each costs a 1 MB stack reservation and a kernel thread create/destroy.
- **Fix:** Create the prioritised seek thread once in the ctor and park it on a `SemaphoreSlim`/`AutoResetEvent`.

#### `_disposed` is a plain `bool` read from several worker loops
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:147`
- **What's wrong:** `Dispose()` writes it from one thread while `EnsureVolumeRampWorker` (862), `ProcessAdvancedEqualizerQueue` (1063), the fade loops (952, 1019, 2567) and the seek worker read it in loops with no barrier. Other shutdown flags in the same class use `volatile`/`Volatile.Read`; this one does not.
- **Fix:** Mark it `volatile` (or read via `Volatile.Read`) for consistency with `_positionTickActive`/`_seekWorkerActive`.

#### `WasapiSilenceKeepAlive` disposes its wake event from inside the worker thread
- **File:** `src/Noctis/Services/WasapiSilenceKeepAlive.cs:241`
- **What's wrong:** `Run()` calls `_wake.Dispose()` when it exits, while `Dispose()` (248) and `NotifyActivity()` (99) may touch `_wake` from the UI/timer thread. `Dispose()` swallows it, but `NotifyActivity` — called from `Play()` (`VlcAudioPlayer.cs:1701`) on the UI thread — does not, so the narrow window between its `_disposed` check and `_wake.Set()` can surface an `ObjectDisposedException` on the UI thread during shutdown.
- **Fix:** Don't dispose `_wake` from the worker; leave it to the disposal path or guard `NotifyActivity` with a try/catch.

#### Shutdown can block the exit thread for ~6.5 s
- **File:** `src/Noctis/Services/VlcAudioPlayer.cs:3326`
- **What's wrong:** `Dispose()` (reached from `Program.Main`'s `provider.Dispose()`) serially waits `DrainPositionTimerCallback` 500 ms (3304) + `DrainSeekWorker` 1000 ms (3305) + `_playbackLock.Wait(3 s)` (3326), and `_keepAlive?.Dispose()` (3364) adds `VlcSilenceKeepAlive`'s `_thread.Join(2000)` (`VlcSilenceKeepAlive.cs:154`). The window is closed by then, so it shows up as the process lingering rather than a frozen UI.
- **Fix:** Run the drains in parallel or shorten the bounds; the native handles are reclaimed by process exit anyway.

# 2. Settings

### HIGH

#### `SyncToSettings` re-serializes a stale snapshot, silently reverting every setting written by another component
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:908`
- **What's wrong:** `SettingsViewModel` loads one `AppSettings` instance at startup (`:681`) and keeps it for the whole session; every `SaveAsync` re-serializes that whole object (`:896`). Other components independently do load→mutate→save on their *own* instance: `LibraryService.ExcludeFilePathsAndCleanFoldersAsync` writes `ExcludedFilePaths` (`Services/LibraryService.cs:811,823`), `EnsureMetadataSchemaUpToDateAsync` writes `MetadataSchemaVersion` (`:1211,1214`), `LyricsViewModel` writes `LyricsBackgroundColorHex`/`LyricsShowArtworkBackground` (`ViewModels/LyricsViewModel.cs:786,726`). `SyncToSettings` never touches any of those four fields, so the next VM save writes the app-start values back over them. Concretely: remove a track → close the window → `MainWindow.CaptureWindowPlacement` unconditionally calls `Settings.SaveAsync()` (`Views/MainWindow.axaml.cs:503`) → the exclusion is erased → next launch's startup scan re-imports the removed file, because `ScanCoreAsync` reads `ExcludedFilePaths` from disk (`Services/LibraryService.cs:111`). The same mechanism reverts a chosen lyrics background on every restart and makes the metadata backfill (`MetadataSchemaVersion` 0→7, a full-library tag re-read) re-run on **every** launch.
- **Fix:** Stop treating `_settings` as the authoritative document. Either re-load settings from disk inside `SaveAsync` under `_saveLock` and merge only the VM-owned fields onto it, or move all settings mutation behind a single shared, serialized `AppSettings` instance with one owner.

#### "Reset Settings" half-resets: custom theme stays active, ~15 toggles keep their values, Last.fm stays logged in
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:2747`
- **What's wrong:** `ConfirmResetLibrary` writes a fresh `AppSettings` to disk (`:2733`) then updates the VM, but `SetActiveThemeFlags("Gray")` never clears `ActiveCustomThemeId` and never clears `CustomThemes` — so `ResolveActiveThemeKey()` (`:1438`) still returns `"Custom:<id>"` and the theme is not reset. It also never resets `MinimizeToTray`, `CloseToTray`, `StartMinimizedToTray`, `RestoreLastTrackOnStartup`, `WebRemoteEnabled`, the five `Show*Column` flags, `PlaybackBarBackgroundOpacity`, `CollapseAlbumEditions`, `EnableAnimatedCovers`, `FfmpegPath`, `ReplayGainPreampDb`, `Profile*`, and never calls `_lastFm?.Logout()` (contrast `_listenBrainz?.Logout()` at `:2828`). Because the next `SaveAsync` runs `SyncToSettings`, all of those stale VM values — including `_settings.LastFmSessionKey = lfm.GetSessionKey()` (`:1002`) — are written straight back over the freshly-defaulted file. Net effect: the reset visibly undoes itself and the Last.fm credential survives while the UI reads "Not connected" (`:2821`). The OS launch-at-login entry is also left registered.
- **Fix:** Rebuild the VM state from `new AppSettings()` field-by-field (or re-run `LoadAsync` after clearing `_settingsLoaded`), clear `ActiveCustomThemeId` + `CustomThemes`, call `_lastFm?.Logout()`, and call `StartupHelper.SetEnabled(false)`.

#### Sliders and the accent colour picker write settings.json on every pointer-move sample
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:1697`
- **What's wrong:** No debounce exists outside the EQ (`QueueEqualizerSave`, `:1157`, 280 ms). `OnReplayGainPreampDbChanged` calls `_audioPlayer.ApplyReplayGain(...)` + `SaveAsync()` on every value change, and `SettingsView.axaml.cs:316` drives `slider.Value` from raw `PointerMoved`. Each call (a) opens the currently playing audio file with TagLib on the calling thread — `ReadReplayGainTags` has no cache (`Services/VlcAudioPlayer.cs:1472,1514`, §1), and (b) runs `SyncToSettings` + `JsonSerializer.SerializeToNode` + DPAPI `Protect` **synchronously on the UI thread** before `SaveJsonAsync`'s `Task.Run` (`Services/PersistenceService.cs:80-91`), plus a temp-file write + rename. The same storm applies to `PlaybackBarBackgroundOpacity` (`SettingsView.axaml:1609` → `:1541`), `CrossfadeDuration` (`SettingsView.axaml:1684` → `:1510`, which additionally re-runs the whole `ApplyAudioSettings` chain), and the accent picker: `ColorPickerFlyout.PushColor` (`Controls/ColorPickerFlyout.axaml.cs:162`) pushes a new hex per pointer-move → `OnCustomAccentHexChanged` (`:161`) → `ApplyAccent` (`:1348`) → `App.SetAccent` rebuilds and re-merges the entire accent `ResourceDictionary` **and** calls `SaveAsync()` (`:1386`).
- **Fix:** Route these through a shared `QueueSettingsSave(ms)` helper; apply the live effect immediately but persist on a ~250 ms trailing edge / drag-end. Cache `ReadReplayGainTags` per `_currentMediaPath`, and move `SerializeToNode` + `ProtectField` inside `SaveJsonAsync`'s `Task.Run`.

> Credentials stored in plaintext on macOS/Linux (`PersistenceService.cs:201`) is reported once in **§4**; it surfaced in this area too.

### MEDIUM

#### The Statistics tab always reports "0 playlists"
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:2302`
- **What's wrong:** `RefreshPlaylistCountAsync()` is the only writer of `TotalPlaylists` (besides the reset path setting it to 0 at `:2853`), and it has **zero call sites** anywhere in `src/Noctis`. The value is bound and displayed at `Views/SettingsView.axaml:2801`, so users with playlists always see "0 playlists".
- **Fix:** Await it from `OpenSettings` (`ViewModels/MainWindowViewModel.cs:49`) and from `OnSelectedSettingsTabChanged` when the Statistics tab opens (`:97`).

#### "Clear Artwork Cache" destroys `artwork/artists` and never recreates it — artist images silently stop caching
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:2867`
- **What's wrong:** `ClearArtworkCache` does `Directory.Delete(artworkDir, true)` then recreates only `artworkDir`. `ArtistImageService` computes `artwork/artists` and calls `Directory.CreateDirectory` exactly once, in its constructor (`Services/ArtistImageService.cs:23-24`), so after a cache clear the subdirectory no longer exists. Every subsequent `File.WriteAllBytesAsync(cachedPath, …)` (`:75`, `:256`) throws `DirectoryNotFoundException` into a swallowing catch (`:84`, `:174`) — artist photos never re-cache until the app is restarted. `ConfirmResetLibrary` gets this right (`:2636`).
- **Fix:** Recreate `Path.Combine(artworkDir, "artists")` in `ClearArtworkCache`, or have `ArtistImageService` ensure the directory on each write.

#### Eleven persisted settings have no UI; five have no reader at all
- **File:** `src/Noctis/Models/AppSettings.cs:77`
- **What's wrong:** Verified by grepping the whole tree. Dead (persisted, never read): `DefaultPageIndex` (`:77` — `GetDefaultPageKey()` hard-returns `"home"` at `SettingsViewModel.cs:670`), `StreamFirstEnabled` (`:241`), `AutoCacheEnabled` (`:244`), `OfflineCacheLimitMb` (`:247`), `ProfileUsername` (`:35` — has an autosave handler at `SettingsViewModel.cs:109` but no control binds it). Read but unreachable from the UI (hand-edit only): `WebRemotePort` (`:153`), `LoonServerUrl` (`:212`), `IgnoredFolderNames` (`:18`), `FolderRules` (`:15`), `SourceConnections` (`:80` — Navidrome/WebDAV/SMB connections are consumed by `UnifiedLibraryService.cs:54` and `NavidromeSyncService.cs:29` but nothing in the app can create one), and `EqualizerEnabled` (`:191` — `OnEqualizerEnabledChanged` exists at `SettingsViewModel.cs:2032`, no toggle in `SettingsView.axaml`, so the EQ can never be switched off).
- **Fix:** Delete the five dead fields or wire them up. Surface at minimum an EQ on/off toggle next to the preset combo and a remote-sources UI.

#### Web Remote port is fixed at 9420 with no way to change it

# 3. Library Data Layer, Persistence & Watching

### CRITICAL

#### Scan of an unmounted/offline music folder wipes the entire library and all user state
- **File:** `src/Noctis/Services/LibraryService.cs:214`
- **What's wrong:** `foreach (var folder in includeRoots) { if (!Directory.Exists(folder)) continue; }` silently skips a root that is offline (external drive unplugged, NAS unreachable, drive letter changed). With 1000 tracks in the library and the root offline at launch, `unchangedCount = 0` and `changedCount = 0`, so the no-op fast path at `:325` (`changedCount == 0 && unchangedCount == originalTrackCount`) does **not** trigger. Execution falls through to `:349`, which sets `_tracks` to an empty list, then `SaveAsync()` at `:377` overwrites `library.json` with `[]` and `:378` clears the SQLite mirror. Every favorite, rating, play count, `DateAdded` and `LastPlayed` is destroyed. `ScanOnStartup` (`MainWindowViewModel.cs:447`) makes this fire automatically, and with multiple roots the same happens per-root. There is no backup file anywhere in the codebase.
- **Fix:** Before publishing `_tracks`, abort the scan if any `includeRoots` entry failed `Directory.Exists` (or produced zero files while previously contributing tracks) — treat it as "root unavailable, keep existing tracks". Add a hard guard: never replace a non-empty `_tracks` with an empty/drastically-smaller set without an explicit user-confirmed rebuild, and keep a rolling `library.json.bak` written before each overwrite.

#### Any deserialization failure of library.json silently yields an empty library, which is then overwritten
- **File:** `src/Noctis/Services/PersistenceService.cs:263`
- **What's wrong:** `LoadJsonAsync` catches every exception, writes a `Debug.WriteLine` (a no-op in Release) and returns `null`. `LibraryService.LoadAsync` (`:828-829`) then takes the `else` branch and leaves `_tracks` empty with no error surfaced. The next `SaveAsync` — a startup scan (`:377`), a favorite toggle, or the 5-second post-play debounce at `PlayerViewModel.cs:1364` — writes the empty set back over `library.json`, permanently discarding ratings/play counts/favorites. Concrete triggers: (a) `JsonOptions` uses `JsonStringEnumConverter` (`PersistenceService.cs:29`), so a single enum string the running build doesn't know (`ReleaseType`, `SourceType`, `OfflineState` — all have grown over releases; a version downgrade or a partially-written file suffices) throws `JsonException` for the *whole* file; (b) one corrupt byte anywhere in a 100k-track file.
- **Fix:** Distinguish "file absent" from "file present but unreadable". On a parse failure, rename aside (`library.corrupt.<ts>.json`), surface a user-visible error, and refuse all writes to `library.json` for that session. Use a tolerant enum converter so unknown members fall back to a default rather than failing the document.

### HIGH

#### Atomic-rename save has no fsync, and the crash-recovery path promotes a possibly-truncated temp file
- **File:** `src/Noctis/Services/PersistenceService.cs:304`
- **What's wrong:** `SaveJsonSerializedAsync` writes `path + ".tmp"` then `File.Move(tempPath, path, overwrite: true)`. The `FileStream` is disposed but never `Flush(flushToDisk: true)`-ed, so on NTFS the rename metadata can reach disk before the file's data pages. A power loss in that window leaves `library.json` present but truncated — which then hits the CRITICAL path above. Separately, `LoadJsonAsync` at `:243-253` moves a leftover `.tmp` into place when the main file is missing; a `.tmp` from a crash *during* serialization is by definition incomplete, so this actively converts "main file missing" into "main file corrupt".
- **Fix:** Call `stream.Flush(flushToDisk: true)` (or `FileOptions.WriteThrough`) before the `File.Move`. Parse-validate the `.tmp` before promoting it, and delete it if it doesn't deserialize.

#### "Remove from Library" permanently blacklists file paths with no way to undo, and silently deletes music-folder entries
- **File:** `src/Noctis/Services/LibraryService.cs:800`
- **What's wrong:** `ExcludeFilePathsAndCleanFoldersAsync` adds every removed path to `settings.ExcludedFilePaths` (`:805-811`), and `ScanCoreAsync` filters those out on every subsequent scan (`:111-114` builds the set, `:223` applies the filter). Worse, `:815-821` then does `settings.MusicFolders.RemoveAll(...)` for any root with zero remaining tracks — removing the last tracks under a root silently deletes the root from Settings and stops the folder watcher for it.

#### Every library mutation rewrites the whole of library.json, bloated ~2× by unmarked computed properties
- **File:** `src/Noctis/Models/Track.cs:375`
- **What's wrong:** Ten get-only computed properties on `Track` lack `[JsonIgnore]` and are serialized on every save: `DurationFormatted` (`:308`), `BitrateFormatted` (`:314`), `SampleRateFormatted` (`:317`), `BitsPerSampleFormatted` (`:320`), `IsLossless` (`:329`), `IsHiResLossless` (`:357`), `AudioQualityBadge` (`:364`), `AudioQualityDescription` (`:375`), `CodecShortName` (`:391`), `AudioQualityDetailedInfo` (`:432`). `AudioQualityDescription` alone emits a 65-character English sentence per track. Combined with `WriteIndented = true` (`PersistenceService.cs:26`), a 100k-track library is on the order of 150–200 MB of JSON — fully re-serialized and re-written by `LibraryService.SaveAsync` (`:874`) on every rating change, favorite toggle, watcher batch, import, and 5 seconds after each track starts (`PlayerViewModel.cs:1364`). - **Fix:** Add `[JsonIgnore]` to all ten. Turn off `WriteIndented` for `library.json`. Longer term, make the already-present SQLite index the write path for per-track mutations so a play-count bump is one UPDATE.

#### The SQLite index is write-only — full clear + reinsert on scan, full upsert on every watcher batch
- **File:** `src/Noctis/Services/ISqliteLibraryIndexService.cs:8`
- **What's wrong:** The interface exposes only `Initialize/MigrateFromJsonIfEmpty/Upsert/Delete/Clear/Count`. There is no query method, and the only consumer is `LibraryService`, which never reads it (`CountAsync` is used solely to decide whether to re-migrate). Yet the write cost is paid constantly: `LibraryService.cs:378-379`, `:434-435`, `:790-791`, `:976-977` do `ClearAsync()` followed by `UpsertTracksAsync(_tracks)` — a 100k-row DELETE plus a 100k-statement transaction — and `ImportFilesAsync` at `:670` upserts the *entire* library on every watcher batch, so a single new file rewrites all 100k rows. - **Fix:** Either wire the index up as the real query backend, or drop the calls. In the meantime, `ImportFilesAsync` should upsert only the imported tracks, and `ClearAsync` + `UpsertTracksAsync` should share one transaction.

- **File:** `src/Noctis/Services/LibraryService.cs:1110`

#### FileSystemWatcher buffer overflow rebuilds watchers but never reconciles the lost events

- **What's wrong:** `OnError` logs and calls `Refresh()`, which only recreates the watchers. #### Startup metadata backfill re-reads tags for every AAC/ALAC track with no progress, cancellation, or shutdown cooperation

#### Track removal is O(tracks × folders) with a `Path.GetFullPath` per element, and the exclusion list grows without bound
- **File:** `src/Noctis/Services/LibraryService.cs:814`
- **What's wrong:** `settings.MusicFolders.RemoveAll(folder => … !remainingPaths.Any(fp => IsUnderRoot(NormalizePath(fp), normalized!)))` linearly scans the full remaining-track set for every configured folder, calling `Path.GetFullPath` (a syscall-backed normalization) per track per folder. # 4. Network, Remote Sources, Credentials & Updater

### CRITICAL

#### Live Last.fm API key **and** shared secret hardcoded in source and in every published binary
- **File:** `src/Noctis/Services/LastFmService.cs:15` (key literal) and `:16` (secret literal)
- **What's wrong:** Both are `private const string` literals. `git log -S'ApiSecret'` returns exactly one commit — `92348d6 2026-03-18 "Initial commit"` — and a hash comparison of those two lines at `92348d6` vs `HEAD` is identical, so the credentials have been public and unrotated for all 481 commits and are embedded in every shipped `Noctis.dll`. The **secret** is what signs every authenticated call in `GenerateSignature` (`:663`), so anyone can impersonate the Noctis application identity: mint auth tokens under it, phish users through the genuine `https://www.last.fm/api/auth/?api_key=<key>` consent screen, act on behalf of any user who has ever authorised it, and burn or get the app's registration revoked. Values are not reproduced here.
- **Fix:** Treat as compromised — revoke and re-issue at Last.fm first. Rewriting git history does not help: the values are in every released binary and every clone. Then either proxy the signed calls through a first-party endpoint (the only way a desktop app can hold a secret), or keep the key client-side and the secret server-side. Load whatever remains from a build-time secret (`AssemblyMetadata` injected by CI) rather than a source literal, and add a pre-commit/CI secret scan.

### HIGH

#### Scrobbler tokens and remote-source passwords are plaintext, mode 0644, on macOS and Linux
- **File:** `src/Noctis/Services/PersistenceService.cs:201`
- **What's wrong:** `ProtectSecret` returns the raw value unchanged whenever `!OperatingSystem.IsWindows()`, so `lastFmSessionKey`, `listenBrainzToken` and every `sourceConnections[].tokenOrPassword` (Navidrome/WebDAV/SMB passwords) are written verbatim into `~/.config/Noctis/settings.json` (`Helpers/AppPaths.cs:23`). The file is created at `:304` with a plain `FileStream` and the directory at `:56` with a plain `Directory.CreateDirectory` — there is no `UnixFileMode` call anywhere in the tree (verified by grep). With a default umask of 022 that is `~/.config/Noctis` at 0755 and `settings.json` at 0644: readable by every other local account and by any unsandboxed process running as another user. Two of three shipped platforms store credentials unprotected.
- **Fix:** Back the non-Windows branch with the platform keystore (macOS Keychain via `security`/`SecItem`; libsecret/`secret-tool` on Linux), dispatching on the existing `enc:` prefix scheme. Immediate mitigation: `File.SetUnixFileMode` 0700 on `AppPaths.DataRoot` and 0600 on `settings.json` (and its `.tmp`) after each atomic rename.

#### Loon: concurrent `ClientWebSocket.SendAsync` aborts artwork responses
- **File:** `src/Noctis/Services/Loon/LoonClient.cs:169`
- **What's wrong:** Every inbound `Request` is dispatched as an independent `Task.Run(() => HandleRequestAsync(...))`, and each handler makes a long series of `SendAsync` calls (`:297`, `:311`, one per chunk). `ClientWebSocket` permits at most one outstanding `SendAsync` and throws `InvalidOperationException("There is already one outstanding 'SendAsync' call…")` otherwise. Two overlapping artwork requests from the relay (Discord retrying, or two viewers resolving the same presence) blow up mid-stream; the exception is swallowed at `:319` and the caller sees a truncated image.
- **Fix:** Serialize all writes through a `SemaphoreSlim(1,1)` inside `SendAsync` (`:359`), and bound in-flight `HandleRequestAsync` work with the same or a second gate.

#### Web remote: an unauthenticated LAN peer can exhaust every connection slot
- **File:** `src/Noctis/Services/WebRemoteServer.cs:157`
- **What's wrong:** `client.ReceiveTimeout = 5000` (`:144`) only affects *synchronous* socket reads; `LineReader.ReadLineAsync` uses `NetworkStream.ReadAsync` (`:200`), which ignores it. A LAN host that opens a TCP connection and sends nothing — or trickles header lines forever into the unbounded drain loop at `:157` — parks a handler indefinitely. Only 16 handlers exist (`MaxConcurrentClients`, `:102`) and excess connections are dropped at `:124`, so 16 idle sockets from any device on the LAN permanently kill the web remote. No token is needed: authorization (`:220`) happens only after the whole request has been read.
- **Fix:** Wrap the request read in a per-connection timeout (`CreateLinkedTokenSource` + `CancelAfter(5s)` passed into `ReadLineAsync`) and cap the header-drain loop at a fixed line count (e.g. 64).

#### Artist image download can hang forever and permanently deadlock the fetch gate
- **File:** `src/Noctis/Services/ArtistImageService.cs:246`
- **What's wrong:** The image fetch uses `HttpCompletionOption.ResponseHeadersRead` and passes **no** `CancellationToken`; the body is drained by `HttpSafety.ReadBytesBoundedAsync(response.Content, MaxImageBytes)` with `ct = default` (`:251`). Because `HttpClient.Timeout` only covers the operation up to the response headers under `ResponseHeadersRead`, a stalled/half-open connection to the Deezer CDN blocks that `ReadAsync` with nothing able to cancel it. `FetchAndCacheAsync` holds `_fetchGate` for the entire sweep (`:118`/`:193`), so one stalled socket blocks every subsequent artist-image fetch for the rest of the process lifetime, and shutdown cannot cancel it (`FetchAndCacheAsync` takes no token at all).
- **Fix:** Give `FetchAndCacheAsync`/`TryDownloadAndSaveAsync` a `CancellationToken`, thread it through `SendAsync` and `ReadBytesBoundedAsync`, and link it to a per-download `CancelAfter` (e.g. 30 s).

### MEDIUM

#### Loon protobuf reader has no bounds checks on server-controlled lengths
- **File:** `src/Noctis/Services/Loon/LoonProtobuf.cs:96`
- **What's wrong:** `ReadRawVarint` indexes `_buf[_pos++]` with no `_pos < _buf.Length` guard, and `ReadString` (`:44`), `ReadBytes` (`:53`) and `ReadSubMessage` (`:62`) cast an attacker-chosen varint to `int` and pass it straight to `Span.Slice(_pos, len)` — a length above `int.MaxValue` becomes negative, and any length past the end overruns. It is memory-safe (spans bounds-check), but every malformed frame from a malicious or hijacked relay tears down the connection into the 5-second reconnect loop at `LoonClient.cs:195`, and a `Hello` malformed at `LoonClient.cs:134` propagates out of `ConnectAsync`.
- **Fix:** Validate in the reader: reject a varint that would run past `_buf.Length`, reject a length-delimited field whose `len` is negative or exceeds `_buf.Length - _pos`, and throw a single `InvalidDataException` the caller already handles.

#### Loon: a hostile relay can flood unbounded concurrent file reads
- **File:** `src/Noctis/Services/Loon/LoonClient.cs:169`
- **What's wrong:** Each `Request` spawns an unthrottled `Task.Run`, and each handler does `File.ReadAllBytesAsync` (`:260`) plus a full Skia decode/resize (`:279`) into memory. There is no cap on in-flight requests, so a compromised relay streaming thousands of `Request` frames drives unbounded parallel I/O and heap allocation. `MaxInboundMessageBytes` (`:330`) bounds a single message, not the request rate.
- **Fix:** Bound concurrency with a `SemaphoreSlim` (2–4 slots) around `HandleRequestAsync`, and drop requests beyond a per-interval rate cap.

#### Navidrome connector accepts `http://` for a credentialed endpoint
- **File:** `src/Noctis/Services/NavidromeMediaSourceConnector.cs:236`
- **What's wrong:** `BuildSubsonicUrl` uses `connection.BaseUriOrPath` verbatim with no scheme validation, so a user who types `http://…` sends `u=<username>&t=MD5(password+salt)&s=<salt>` in cleartext on every request. MD5(password‖salt) with the salt on the wire is trivially dictionary-attackable offline, and the username leaks outright. There is no UI warning.
- **Fix:** Require `https://` in `ValidateConnectionAsync` (or an explicit per-connection opt-in with a visible warning), and reject non-http(s) schemes outright.

#### Navidrome responses bypass the `HttpSafety` byte caps
- **File:** `src/Noctis/Services/NavidromeMediaSourceConnector.cs:27`
- **What's wrong:** `ValidateConnectionAsync` (`:27`), `FetchAlbumsAsync` (`:79`) and `FetchSongsForAlbumAsync` (`:111`) all use `_http.GetStringAsync`, which buffers the entire body with no cap — the only limit is `MaxResponseContentBufferSize` (2 GB). #### Updater launches an elevated installer with no code-signature verification
- **File:** `src/Noctis/Services/UpdateService.cs:507`
- **What's wrong:** `LaunchInstaller` runs the downloaded `.exe` with `UseShellExecute = true` and `/SILENT`, triggering a UAC elevation prompt. The Authenticode signature on the shipped installer is never checked, and neither is the macOS `.dmg` codesign. (Related: the manifest is generated by hand outside CI — §12.)
- **Fix:** Before launching, verify the Authenticode signature and publisher subject on Windows (`WinVerifyTrust` or `X509Certificate.CreateFromSignedFile` + expected subject) and `codesign --verify --deep` / expected Team ID on macOS. Refuse to launch on failure.

#### Developer-mode version manager installs without requiring the checksums manifest
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:3252`
- **What's wrong:** The normal update path passes `requireChecksums: true` (`:3030`), but the version-manager install path calls `DownloadInstallerAsync(item.Info, progress, _devCts.Token)`, which defaults to `requireChecksums: false` (`UpdateService.cs:389`), then immediately elevates via `LaunchInstaller` (`:3255`). #### Downloaded-asset filename from the GitHub API is used unsanitized as a file path
- **File:** `src/Noctis/ViewModels/SettingsViewModel.cs:3307`
- **What's wrong:** `Path.Combine(downloads, item.Info.InstallerAssetName ?? …)` builds the save path from the release asset's `name` field (`UpdateService.cs:721`). #### Artist-image rate limit is applied only on the failure path
- **File:** `src/Noctis/Services/ArtistImageService.cs:188`

- **Fix:** Check `IsSuccessStatusCode` and the Last.fm error code, surface a persistent "scrobbling failed" indicator in Settings, and persist unsent listens to a small on-disk queue flushed on reconnect.

#### Web remote binds `0.0.0.0`
- **File:** `src/Noctis/Services/WebRemoteServer.cs:46`
- **What's wrong:** `new TcpListener(IPAddress.Any, port)` listens on every interface, including a public one on a machine without a firewall. #### HLS animated-cover download has no cap on part count or output size
- **File:** `src/Noctis/Services/ITunesArtworkService.cs:214`
- **What's wrong:** `DownloadHlsVariantAsMp4Async` appends every non-comment line of the media playlist as a segment URI and downloads each into memory at up to `MaxAnimatedCoverBytes` (256 MB, `:97`) before appending to the output file (`:223`–`:227`). - **Fix:** Cap the segment count and cumulative bytes written (e.g. 512 MB) with an early abort + cleanup, stream each part to the file instead of buffering it whole, and require `https` + an Apple host in the primary regex.

- **File:** `src/Noctis/Services/AudioConverterService.cs:342` (with `src/Noctis/Helpers/TitleFormatter.cs:68`)
- **What's wrong:** `ComputeOutputPath` builds the destination as `Path.Combine(dir, TitleFormatter.Expand(pattern, track, sanitizeForFilename: true) + ext)`. `SanitizeFilenameSegment` (`TitleFormatter.cs:62-74`) replaces only `\ : * ? #### Startup runs inside an unguarded `async void` handler — one throw kills the app with a blank window
- **File:** `src/Noctis/Views/MainWindow.axaml.cs:99`

### CRITICAL

#### "Save analysis to file tags" creates a permanent re-analyze / re-write loop over every track
- **File:** `src/Noctis/Services/AudioAnalysis/AudioAnalysisCoordinator.cs:148`
- **What's wrong:** The key is written with `AdvancedTagIO.WriteCustomField(file, "TKEY", …)`, which for ID3v2 creates a **TXXX frame with description "TKEY"** (`Services/AdvancedTagIO.cs:446`), for Xiph a field literally named `TKEY` (`:454`), and for MP4 a `com.apple.iTunes:TKEY` dashbox. `MetadataService.ReadMusicalKey` reads the *standard* ID3 `TKEY` text frame (`Services/MetadataService.cs:985`) and then only accepts TXXX/Xiph/dashbox names `INITIALKEY` / `KEY` / `MUSICALKEY` (`:992`, `:1008`, `:1021`). "TKEY" is in none of those lists, so nothing — not Noctis, not foobar/Serato/Mixed In Key — ever reads the value back. That becomes a loop: (1) backfill analyzes track X and rewrites the file; (2) mtime+size change and `LibraryWatcherService` watches `NotifyFilters.LastWrite | NotifyFilters.Size` (`Services/LibraryWatcherService.cs:72`, enabled by default), so `ImportFilesAsync` re-imports it; (3) `CopyMutableTrackState` does **not** carry `Bpm`/`MusicalKey` (`Services/LibraryService.cs:1128-1148`) and the fresh read yields `MusicalKey = ""`, so the analyzed key is lost; (4) `LibraryUpdated` fires (`LibraryService.cs:671`) → `StartBackfill` (`App.axaml.cs:112`) → `NeedsAnalysis` is true again; (5) the SQLite cache row was written **before** the tag write with the pre-write size/mtime (`:105-107`), so the signature check at `:99` misses → full ffmpeg re-decode; (6) key set again → `changed = true` → `TryWriteTags` rewrites the file → back to (2). Every affected track is decoded and fully rewritten by TagLib forever, burning CPU and disk and multiplying the chance of a truncated file on a crash or power loss.
- **Fix:** Write the key with the format-correct field, e.g. `AdvancedTagIO.WriteField(file, "TKEY", "INITIALKEY", null, key)` (matching what `ReadMusicalKey` accepts), and add `INITIALKEY` to the Apple dashbox write. Break the loop at two more points: re-`Upsert` the store record with the post-write `FileInfo` size/mtime after `TryWriteTags` succeeds, and add `Bpm`/`MusicalKey` to `CopyMutableTrackState`.

#### `KeyDetector` silently returns "C major" for degenerate or NaN input
- **File:** `src/Noctis/Services/AudioAnalysis/KeyDetector.cs:61`

#### ReplayGain album gain is an unweighted mean of per-track LUFS
- **File:** `src/Noctis/Services/ReplayGainScannerService.cs:119`
- **What's wrong:** `grp.Average(t => measured[t].IntegratedLufs)` averages loudness values in the log domain with equal weight per track. An album with nine 4-minute tracks at −9 LUFS and one 15-second interlude at −30 LUFS yields a mean of −11.1 LUFS (album gain −6.9 dB) where a duration/energy-weighted result is ≈ −9.1 LUFS (album gain −8.9 dB) — a 2 dB error applied to the whole album. - **What's wrong:** `trackGainDb = ReferenceLufs - r.IntegratedLufs` has no bound. #### Cancelling a ReplayGain scan during measurement discards every measurement taken
- **File:** `src/Noctis/Services/ReplayGainScannerService.cs:96`
- **What's wrong:** Pass 1 measures *all* tracks before pass 2 (`:127`) writes any tag, because album mode needs the group aggregates first. `ct.ThrowIfCancellationRequested()` at `:96` aborts out of `ScanAsync`, so cancelling after 400 of 500 tracks throws away 400 completed ffmpeg loudness measurements with zero tags written and nothing cached. - **File:** `src/Noctis/Views/ReplayGainScannerDialog.axaml:62`

- **File:** `src/Noctis/Models/Track.cs:105`
- **What's wrong:** `Bpm` and `MusicalKey` (`:108`) are plain auto-properties on an `ObservableObject`, so assigning them at `AudioAnalysisCoordinator.cs:111-113` raises no `PropertyChanged`. - **File:** `src/Noctis/Views/ReplayGainScannerDialog.axaml.cs:16`
- **What's wrong:** The only cancellation path is the `Cancel` command (`ViewModels/ReplayGainScannerViewModel.cs:124-129`); the window has no `Closing` handler. #### No re-analyze, no cache visibility, and only the first 120 s of a track is analyzed
- **File:** `src/Noctis/Services/AudioAnalysis/AudioAnalysisService.cs:14`
- **What's wrong:** `MaxSeconds = 120` means BPM/key come from the first two minutes only — wrong for DJ mixes, long ambient intros, and multi-movement files. ### HIGH

#### Known-vulnerable native SQLite ships in every release (CVE-2025-6965, GHSA-2m69-gcr7-jv3q, High)
- **File:** `src/Noctis/Noctis.csproj:91`
- **What's wrong:** `Microsoft.Data.Sqlite 8.0.11` resolves `SQLitePCLRaw.lib.e_sqlite3 2.1.6`, which NuGet audit flags High for CVE-2025-6965 (SQLite < 3.50.2 — an aggregate-term count can exceed available columns → memory corruption). Practical exploitability is limited because Noctis authors all its own SQL, so this is "vulnerable component shipped" rather than a directly reachable exploit — but it is a High advisory in the release payload with a trivial fix. The same advisory fires for `tests/Noctis.Tests/Noctis.Tests.csproj`.
- **Fix:** Add an explicit `<PackageReference Include="SQLitePCLRaw.bundle_e_sqlite3" Version="2.1.12" />` to float the native past the fix, or bump `Microsoft.Data.Sqlite` off the 8.0.x line. Re-run `dotnet list package --vulnerable --include-transitive` to confirm clean.

#### `komac` is downloaded without checksum verification and executed with a GitHub PAT in its environment
- **File:** `.github/workflows/package-managers.yml:114` (through `:120`, used at `:131`/`:134` with `GITHUB_TOKEN: ${{ secrets.WINGET_PAT }}` at `:137`)
- **What's wrong:** The job `curl`s `komac-2.16.0-x86_64-unknown-linux-gnu.tar.gz` from a third-party GitHub release, `sudo install -m755`s it into `/usr/local/bin`, and runs it with `WINGET_PAT` exported. There is **no SHA-256 check** — unlike every ffmpeg/appimagetool download in `dotnet.yml`, which are all pinned *and* hash-verified. A replaced release asset upstream (or a compromised upstream account re-uploading that tag) yields arbitrary code execution on a runner holding a PAT able to push to `heartached/scoop-bucket` and to fork/PR `microsoft/winget-pkgs`.
- **Fix:** Pin and verify — `echo "<sha256>  komac.tar.gz" | sha256sum -c -` before extracting, exactly as `dotnet.yml:100`/`:114`/`:295` already do. Also scope `WINGET_PAT` to the minimum and prefer a fine-grained token.

#### macOS code-signing failure is downgraded to a warning — a broken-signature build ships anyway
- **File:** `.github/workflows/dotnet.yml:207`
- **What's wrong:** `codesign --verify --deep --verbose=2 "$APP" || echo "::warning::codesign verify reported issues on $APP"` — the `||` swallows a non-zero exit, so the `.dmg`/`.zip` are still built and uploaded from an app bundle whose signature did not verify. On Apple Silicon an invalidly signed Mach-O is SIGKILLed at exec (the "bounces in the dock and quits" failure this repo has already shipped once), and this step is the only thing standing between a signing regression and a dead macOS release.
- **Fix:** Drop the `|| echo` so the step fails the job. If runner flakiness was the reason for the soft-fail, retry the signing — don't ignore the verify.

#### Release artifacts are unsigned and the integrity manifest is unsigned and produced outside CI
- **File:** `.github/workflows/dotnet.yml:306` (upload steps — no signing, no `SHA256SUMS` generation anywhere in the workflow); consumed by `src/Noctis/Services/UpdateService.cs:417`
- **What's wrong:** CI builds and uploads the artifacts but never produces a checksum manifest and never signs anything; `SHA256SUMS` is created by hand during the manual release step. The in-app updater does the right thing at runtime — `UpdateService.cs:410` rejects non-GitHub URLs, `:417` fails closed when `requireChecksums` is set, `:474`–`:487` verifies SHA-256 before launching, and `SettingsViewModel.cs:3030` passes `requireChecksums: true` — but it then launches the downloaded `Setup.exe` with `UseShellExecute = true`, i.e. **with UAC elevation** (`:516`–`:520`). Because the manifest is unsigned and lives in the same release as the binary, the checksum only protects against transport corruption, not a compromised release. The Windows installer is unsigned (acknowledged in `README.md`), the macOS bundle is only ad-hoc signed and not notarised (`dotnet.yml:206`), and the AppImage is unsigned. See also §4 (no Authenticode check before elevation).
- **Fix:** Generate `SHA256SUMS` in CI over every artifact (a final job that downloads all matrix artifacts and `sha256sum`s them) so it can never drift from what was built, and sign it with a release GPG key published in the repo. Longer term, Azure Trusted Signing / SignPath OSS for the Windows installer and Apple notarisation for the `.dmg` remove the "unsigned elevated execution" class entirely.

#### The Inno installer omits `ffmpeg.exe`, so the primary Windows install channel ships without the converter backend
- **File:** `installer.iss:39` (the `[Files]` section, lines 40–43)
- **What's wrong:** `[Files]` copies only `Noctis.exe`, `Noctis.pdb`, `*.dll` and `libvlc\*` from `publish\win-x64\`. `publish\win-x64\ffmpeg.exe` (87,638,016 bytes, present on disk with the same extraction timestamp as the rest of the folder) matches none of those patterns. CI goes to real trouble to pin and SHA-256-verify that binary "so users don't need a system install" (`dotnet.yml:81`–`:92`), and the portable `.zip` gets it — but `Noctis-v{ver}-Setup.exe`, which is what winget and Chocolatey serve, does not. Corroborated by size: the covered payload is ~430 MB and compresses to the observed 99.4 MB setup; adding 87 MB would visibly grow it. `AudioConverterService.GetFfmpegPath()` (`src/Noctis/Services/AudioConverterService.cs:145`–`:164`) looks next to the exe, then falls back to `PATH`, then returns `null` — so installer users silently lose the Audio Converter, the ReplayGain scanner (`ReplayGainScannerService.cs:80`) and share-clip video export unless they happen to have ffmpeg on `PATH`.
- **Fix:** Add `Source: "publish\win-x64\ffmpeg.exe"; DestDir: "{app}"; Flags: ignoreversion skipifsourcedoesntexist`. Better, replace the four hand-written patterns with `Source: "publish\win-x64\*"; Flags: ignoreversion recursesubdirs createallsubdirs` plus an `Excludes:` for `*.pdb`, so the installer can never again silently diverge from what CI publishes. (Verified separately that the missing `Noctis.runtimeconfig.json`/`Noctis.deps.json` are *not* fatal — a self-contained .NET 8 apphost still starts without them.)

#### Untrusted-input interpolation directly into `run:` shell bodies (template injection)
- **File:** `.github/workflows/package-managers.yml:33` and `:35` (also `:47`, `:84`–`:86`, `:105`, `:125`–`:126`)
- **What's wrong:** `TAG="${{ github.event.release.tag_name }}"` and `TAG="${{ inputs.tag }}"` are substituted into the script text before `bash` sees it, so a tag name or dispatch input containing shell metacharacters executes in a job whose downstream jobs hold `SCOOP_BUCKET_TOKEN` and `WINGET_PAT`. Practical risk is limited (both inputs require write access today), but this is the standard GitHub-documented injection sink. Relatedly, `${{ secrets.WINGET_PAT }}` is interpolated inline into a `curl -H` argument at `:128`, putting the PAT in the runner's process arguments.

- **What's wrong:** `publish/win-x64` measures 517,459,770 bytes, of which `libvlc/` alone is 292,821,356 — the complete VLC 3.x plugin set, including video decoders, streaming outputs, visualisations and access modules a music player never loads. The oversized plugin tree is also attack surface: every VLC demuxer in that folder is reachable the moment a user opens a malformed file.
- **Fix:** Prune `libvlc/plugins/` to the audio/access/demux/codec modules actually used (a post-publish allowlist step in CI, validated by a smoke launch) — the single biggest win for installer size, download time and attack surface. Separately, enable `<PublishReadyToRun>true</PublishReadyToRun>` for the release RIDs and measure the startup delta. Trimming is not realistic with Avalonia XAML + reflection-heavy code.
